# Рекомендации для разработки виджетов amoCRM/Kommo — уроки проекта «Дубли»

Формат: **болячка → вывод/правило**. В конце — пред-полётный чек-лист и что
вынести в переиспользуемый шаблон.

## 1. Манифест и соответствие описанию (модерация)
- Описание строго = реализованный функционал. В `locations` — только то, что
  реально рендерится. «Мёртвые» i18n-ключи и код удалять.
- `interface_version: 2`, `oauth: "Y"` (если OAuth), обязательные поля установки
  — `required`, секреты в полях — тип `pass` (маскирование).
- Все видимые строки — из i18n; **паритет `ru`/`en`**; хардкода нет.
- Реализовать `destroy()`; в `bind_actions` — namespace и `.off()` перед `.on()`;
  ноль ошибок в консоли на чистом аккаунте.

## 2. Логотипы и ассеты витрины
- Свериться с размерами заранее и **добавить проверку в `validate.py`**, чтобы
  падать локально, а не в кабинете.
- Справочные размеры (по докам amoCRM): логотип **108×108**, иконка **400×272**,
  тур **1188×616**, скриншоты витрины **1280×800** (сверяться с актуальными).

## 3. Публикация: `code`/`secret_key` — главный источник боли
- Публичная (маркетплейс) интеграция ≠ приватная. Создаётся в **amoМаркет →
  «Моё приложение»**, имеет **свой `code`** (вручную, **неизменяем**) и
  **`secret_key`** (генерируется, **показывается один раз**).
- Секрет читать **точно из DOM/буфера**, не со скриншота (l/I/1, O/0).
- Секрет сгенерировать **один раз**, вписать одно значение в
  `manifest.widget.secret_key` (архив) **и** в `.env`, больше не трогать.
- Диагностика загрузки: сверить **SHA-256** архива в браузере с исходником;
  заголовок ZIP = `50 4B 03 04`. `manifest.json` в корне, без `__MACOSX/`/
  `.DS_Store`; версию бампать при каждой загрузке.
- Бывает, кабинет отклоняет корректный секрет (рассинхрон «Ключи» ↔ валидатор
  или требуется включить «Продавать через amoCRM») — держать наготове запрос в
  поддержку с фактами (code, ID интеграции, свежесть секрета, целостность байт).

## 4. OAuth и несколько клиентов
- Публичная интеграция получает **новый** `client_id`/`secret`. Бэкенд должен
  авторизовать несколько клиентов (реестр `client_id → {secret, redirect}`).
- `redirect_uri` в кабинете = бэкенд точь-в-точь (http/https, слэш, порт).
  Access-токен 24 ч — refresh-ротация, токены шифровать.

## 5. Деплой и инфраструктура (облачный Cowork)
- Исходящий SSH (22) из сэндбокса закрыт (443 открыт) → деплой через **мост к
  Маку** (osascript → ssh) или таск «на компьютере».
- Через AppleScript→ssh→bash ломаются кавычки → всё через **base64**.
- Мост отваливается — повторять, не долбить. `.env` — бэкап, без дублей,
  секреты не в git. Длинный build — в фоне. Приватный ключ — `chmod 600`.

## 6. Биллинг (для платных виджетов)
- При «Внешней оплате» amoCRM биллинг НЕ ведёт → источник истины ваш бэкенд.
  Модель: `subscriptions(status, paid_till, trial_ends_at, grace_until, users,
  months, payment_method)` + `payments(payment_id UNIQUE, ...)`; продление
  идемпотентно по `payment_id`; `paid_till = max(now, paid_till) + months`.
- Два трека: карта/СБП → рекуррент ЮKassa + dunning; счёт юрлицу → нет
  авто-списаний, подтверждение + grace-дни, матчинг по номеру счёта.
- 54-ФЗ: карта физлица → `receipt` (email/тел + `vat_code`); безнал по счёту —
  чек обычно не нужен.
- Вендор-панель (AdminJS) с первого дня; гейтинг: `now ≤ paid_till ИЛИ
  grace_until ИЛИ trial`.

## 7. Вендор-CRM и кастомные поля
- Перед записью значения знать **тип поля** (lead/contact/company) и писать в
  правильную сущность (иначе `400 NotSupportedChoice`).
- Дедуп по уникальному ключу ДО создания; бэкфилл идемпотентный;
  долгоживущий токен (external integration) для фоновых задач.

## 8. Процесс и инженерная гигиена
- `scripts/validate.py` до загрузки: manifest в корне, размеры логотипов,
  паритет i18n, отсутствие хардкода/console, чистота zip, версия-бамп.
- Секреты только в `.env`/`.publish.env`; в доки/чат — placeholder.
- Проверять измеримо (HTTP-коды, sha256, тесты, диффы), не «на глаз».

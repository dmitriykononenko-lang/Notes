# Рекомендации для следующего виджета amoCRM + биллинг

Уроки, собранные на проекте «Дубли» — чтобы сразу сделать лучше. Документ
обобщает реальные грабли при запуске оплаты и интеграции с вендорской amoCRM и
даёт правила «как надо с самого начала». Разбито по слоям: виджет → бэкенд →
оплата → вендорская CRM → жизненный цикл → тестирование. В конце — чек-лист.

## 1. Виджет (frontend)
- **1.1. Локации ↔ функции.** Каждая заявленная возможность = локация
  (`lcard-1`/`ccard-1`/`comcard-1`/…) + колбэк `render` + i18n. Код/строки без
  локаций удалять — иначе функция «есть в коде», но не появляется.
- **1.2. `code` и `secret_key` в манифесте с первого дня.** Для приватной и
  маркетплейс-интеграции обязательны, совпадают с кабинетом разработчика.
- **1.3. Типы полей настроек.** Секреты — тип `pass`, не `text`. Функционально
  обязательные (`backend_url`, `security_key`) — `required: true`.
- **1.4. Экранирование (XSS).** Все динамические значения — через `escapeHtml`
  (email, телефон, субдомен, имена, суммы). Лучше — Twig `templates/*.twig`.
- **1.5. Обработчики событий — с namespace.** При `init_once: false` виджет
  пересоздаётся на SPA-навигации: `.off('click.mywidget').on('click.mywidget', …)`.
- **1.6. Ошибки — показывать пользователю.** Не маскировать 503/ошибки бэкенда
  заглушками «скоро будет». `AMOCRM.notifications.add_alert` + логировать причину.
- **1.7. Версионирование и синхронность.** Виджет сам не обновляется —
  пересобирать zip, поднимать `version` (semver). Бэкенд и виджет катить
  согласованными версиями.
- **1.8. i18n-паритет.** Ключи из `manifest`/`script.js` есть во всех локалях.
- **1.9. Упаковка.** `manifest.json` в корне архива; исключать `.DS_Store`/
  `__MACOSX`; `installation` — по спецификации (проверить формат под свою
  `interface_version`).

## 2. Бэкенд: конфигурация и секреты
- **2.1. `env_file` с первого дня.** `env_file: [.env]` + критичные значения
  продублировать в `environment:`. Новая переменная — сразу в `.env.example` и
  в проброс. (Самая дорогая ошибка «Дублей»: переменные были в `.env`, но не
  пробрасывались в контейнер → 503.)
- **2.2. Валидация env на старте (fail-fast).** zod-схема; пустые строки → `default()`.
- **2.3. Секреты — только в `.env`, не в git.** В репо — плейсхолдеры в `.env.example`.
- **2.4. Общий секрет виджет↔бэкенд.** `WEBHOOK_SECURITY_KEY` — заголовком
  (`X-Security-Key`), не в URL; значение в настройках виджета = `.env`.

## 3. Оплата (ЮKassa / эквайринг РФ)
- **3.1. 54-ФЗ / чек с самого начала.** Каждый платёж — `receipt` (позиции +
  `vat_code` + контакт). Сделать настраиваемым: `YOOKASSA_FISCAL`,
  `YOOKASSA_VAT_CODE` (УСН = 1 «без НДС»).
- **3.2. Контакт покупателя для чека обязателен.** Поле email/телефон в форме
  оплаты; бэкенд принимает и валидирует (пустой → понятная ошибка, не 500).
- **3.3. Хостед-оплата и вебхук.** Только hosted-страница ЮKassa
  (`confirmation_url` → redirect). Вебхук перепроверять по id через API,
  отвечать 200. Опц. IP-allowlist на nginx.
- **3.4. Тест без реальных денег.** Тестовый магазин ЮKassa + `test_` ключ.

## 4. Интеграция с вендорской (своей) amoCRM
- **4.1. Долгосрочный токен, не OAuth-установка.** Внешняя (API) интеграция в
  вендор-аккаунте + долгосрочный токен в `.env` (`VENDOR_AMOCRM_TOKEN`).
- **4.2. Проверять сущность кастом-поля.** `GET /api/v4/{leads|contacts|
  companies}/custom_fields` — найти `field_id` и его сущность/тип, не угадывать
  по подписи. (Поле «ID аккаунта amo» оказалось полем КОМПАНИИ → `400
  NotSupportedChoice` при записи в lead.)
- **4.3. Модель сделки-счёта.** `account_id` — на компании, телефон/email — на
  контакте, оба линковать к сделке (`POST /api/v4/leads/{id}/link`). Не писать
  контакты только в примечание.
- **4.4. Дедуп обязателен.** Искать компанию/контакт перед созданием; хранить
  `vendor_company_id`/`vendor_lead_id`.
- **4.5. Субдомен/ID единообразно.** Нормализовать формат (или числовой
  `account_id`), покрыть тестом.
- **4.6. Этапы — по явным ID, не по названию.** `VENDOR_AMOCRM_STATUS_*` явными
  ID (`GET /api/v4/leads/pipelines/{id}`).

## 5. Жизненный цикл: установка → счёт → оплата
- **5.1. Сделка при установке** (`onInstall` → этап «установлен»), best-effort.
- **5.2. Бэкфилл** для уже установленных (идемпотентный, пропускает с
  `vendor_lead_id`).
- **5.3. Идемпотентность и «оживление».** Проверять по `vendor_lead_id`; 404 →
  пересоздать; 5xx → ретрай/бэкфилл, не дубль.
- **5.4. Данные приходят не сразу.** Телефон появляется позже — поэтапное
  обогащение (`saveContact`).

## 6. Тестирование и наблюдаемость
- **6.1. Серверные smoke-тесты каждого пути** (`/health`, `checkout`,
  `invoice-request`), включая негативные (без email → 400, не 500).
- **6.2. Сквозной прогон в браузере** (оплата открыла ЮKassa с верным продавцом;
  счёт создал сделку в нужной воронке с привязками).
- **6.3. Логи с контекстом** (`account_id`, суммы, id сущностей). Best-effort не
  роняет основной запрос, но логирует сбой.
- **6.4. Понятные тексты ошибок API** (отражают настоящую причину).

## Чек-лист перед запуском биллинга нового виджета
- [ ] `docker-compose`: `env_file: .env` + критичные в `environment`; всё новое — в `.env.example`.
- [ ] Валидация env на старте (fail-fast), пустые строки → default.
- [ ] Секреты только в `.env`, плейсхолдеры в `.env.example`, ничего в git.
- [ ] ЮKassa: `receipt` (54-ФЗ) с `vat_code`, поле email/телефон в форме, валидация.
- [ ] Вебхук ЮKassa: перепроверка по id, ответ 200, (опц.) IP-allowlist.
- [ ] Вендор-CRM: внешняя интеграция + долгосрочный токен в `.env`.
- [ ] Кастом-поля: сверены `field_id` и сущность (lead/contact/company) через API.
- [ ] Сделка-счёт: компания (account_id) + контакт (телефон/email) линкуются к сделке.
- [ ] Дедуп компаний/контактов/сделок; хранение `vendor_*_id`.
- [ ] Этапы воронки — явными ID в `.env`.
- [ ] Сделка при установке + бэкфилл + идемпотентность/оживление.
- [ ] Виджет: локации ↔ функции, `code`/`secret_key`, `pass` для секретов,
      `required` где нужно, escapeHtml, i18n-паритет, semver, zip с manifest в корне.
- [ ] Виджет показывает реальные ошибки, не заглушки.
- [ ] Smoke-тесты (`health`/`checkout`/`invoice`) + сквозной прогон + тестовый магазин ЮKassa.
